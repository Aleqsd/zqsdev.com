# zqsdev.com Operations Notes

This file captures the details an operator or automation agent needs to keep the site and its API healthy.

## Site Worker (zqsdev)
- Hosting: Cloudflare Worker with static assets (`wrangler.jsonc`, `worker/index.js`), DNS on Cloudflare. Rules live in `site-rules.json` (redirects, rewrites, headers, and `/api/*` → `service:API`); the Python tests read the same file.
- Workers Builds runs `npx wrangler deploy` on every push to `main`, with no build command. Always run `make build && make test` locally so the committed `static/` assets and `build_id.js` are fresh before pushing.
- `/api/*` on the apex is forwarded unchanged (method, headers including the edge's `CF-Connecting-IP`, streamed body) with `env.API.fetch(request)` to the `zqsdev-api` Worker, and the call is registered in `ctx.waitUntil` so a visitor who disconnects does not cancel a paid call. A binding failure answers `502 Bad gateway` with HSTS; the frontend then falls back to `./data/*.json`.
- `www` redirects to the apex (and breaks `POST /api/ai`); `cv.zqsdev.com/api/*` is the CV rewrite and answers the 404 page; the bare `/api` path is a 404 page too.
- Ordering rule: `zqsdev-api` must exist before a site deploy that declares the `API` binding. Never delete or rename `zqsdev-api` while `wrangler.jsonc` declares it.

## API Worker (zqsdev-api)
- Rust (workers-rs 0.9.0) in `api/`, a standalone Cargo workspace with its own `Cargo.lock`, configured by `api/wrangler.jsonc`. Pure logic lives in `api/src/core` (native tests, real SQLite through rusqlite); the runtime adapters in `api/src/glue` (fetch handler, `Ledger` Durable Object, `transactionSync`, OpenAI fetch with its own abort timer and a 64 KiB reply cap).
- Ingress: only the `API` service binding of the site Worker, no route. `workers_dev` is on only for the canary and the 7-day soak (`https://zqsdev-api.aleqsd.workers.dev`); the cleanup commit sets it to `false`.
- Routes: `GET|HEAD /api/data` and `/api/version` (compile-time constants), `GET|HEAD /api/health`, `POST /api/ai`, `POST /api/log/command`, `POST /api/admin/*`. Any other `/api/*` request gets 404 with `Cache-Control: no-store`.
- Secrets, never in the repo, the chat or a command line: `OPENAI_API_KEY` and `ADMIN_TOKEN` (at least 32 characters, generated with `python3 -c "import secrets; print(secrets.token_urlsafe(32))"` and kept in a password manager). From `api/`: `printf '%s' "$OPENAI_API_KEY" | npx wrangler secret put OPENAI_API_KEY` (PowerShell: `$env:OPENAI_API_KEY | npx wrangler secret put OPENAI_API_KEY`). Locally they go in `api/.dev.vars` (copy `api/.dev.vars.example`; git ignores it).
- Vars (`api/wrangler.jsonc`): `OPENAI_MODEL` (`gpt-6-luna`; `gpt-5.6-luna` also has built-in prices), `AI_MINUTE|HOUR|DAY|MONTH_BUDGET_USD` (0.5 / 2 / 2 / 10), `AI_DAILY_MAX_CALLS` (2,000 admitted AI calls per UTC day), `COMMAND_LOG_DAILY_CAP` (10,000), `LOG_RETENTION_DAYS` (0 = never delete logs), `LOG_TEXT_BUDGET_MB` (256), `LOG_LEVEL`. The optional `AI_*_USD_PER_MILLION` prices override the built-in table; a model outside it needs all four, and an invalid price disables AI (`ai_not_configured`). `OPENAI_BASE_URL` only points local tests at the stub (loopback only; any other value disables AI). The native test `production_config_is_valid` checks the committed file before every deploy.
- State: one SQLite-backed Durable Object class `Ledger`, single instance `zqs-ledger-v1` (location hint `weur`), holding the spend ledger (integer nano-USD, rolling minute/hour/day/30-day windows), the per-IP windows (4/s, 8/min, 60/h, 120/day; IPv6 per /64; 4,096 IPs per 24 h), the 2 provider slots (20 s leases), the global command window (120 per 60 s), the daily caps and the question, answer and command logs with visitor IPs. Every write runs inside `transactionSync`; maintenance runs lazily (at most hourly, bounded batches): no alarm, no cron. Schema changes must stay additive so that rollbacks keep working.
- Storage guard: stored text is capped (questions and answers 2,000 characters, commands 200). Beyond `LOG_TEXT_BUDGET_MB` rows are kept without their text and `/api/health` reports `text_full`; `db_high` means more than 768 MiB. Recovery without a redeploy: export, then `purge` (or set `LOG_RETENTION_DAYS`).
- Admin: `scripts/zqs_admin.py` (`--api` defaults to `https://zqsdev.com`) with the token from `ZQS_ADMIN_TOKEN` or a no-echo prompt; it travels only in the JSON body. Subcommands: `stats`; `export --table questions|commands|ledger [--after C] [--last N] [--out F] [--vps-json]` (the legacy `command`, `ai_question` and `ai_answer` JSON lines plus `ai_usage` and `ai_failure`; `--vps-json` rebuilds the VPS `ai-budget.json`); `import-ledger --file F [--chunk 250] [--close]` (idempotent, keyed on the VPS charge id); `purge --table questions|commands --before <unix|YYYY-MM-DD>` (questions inside the 30-day window are always kept); `rebuild` (repairs an invalid ledger, which otherwise fails closed with `budget_unavailable`). Copies of the VPS ledger (`ai-budget*.json`) are git-ignored; delete them after use.
- Deploy loop: commit, then `make deploy-api`. It refuses uncommitted tracked changes and a set `ZQS_FAULT_INJECTION`, runs `cargo test --manifest-path api/Cargo.toml --lib`, deploys with `ZQS_BUILD_COMMIT=$(git rev-parse HEAD) npx wrangler deploy`, then `scripts/verify_api_deploy.py` polls `/api/version` until it reports `VERSION` and HEAD, checks `ai_configured`, the model, `/api/health` and `/api/data`, and runs `wrangler rollback` on failure. The first deploy (nothing to roll back to) uses `make deploy-api API_VERIFY_URL=https://zqsdev-api.aleqsd.workers.dev VERIFY_FLAGS=--no-rollback`. `make api-dry-run` builds and validates without uploading. Workers Builds has no Rust: `api/` is always deployed from a developer machine.
- Rollback: automatic after a failed post-deploy check, otherwise `cd api && npx wrangler rollback --message "…"` (under a minute; Durable Object data is untouched). Model regression: set `OPENAI_MODEL=gpt-5.6-luna` in `api/wrangler.jsonc`, then `make deploy-api`.
- Monitoring: `GET /api/health` (`{"ok":true,…}`, `Cache-Control: no-store`; UptimeRobot keyword `"ok":true` every 5 min), `make version-check`, `make api-tail` (`wrangler tail`), Workers Logs (one JSON object per line, emoji-prefixed `msg`, no question or answer text, IP, token or provider body), `zqs_admin.py stats` (window sums, slots, counters, sizes; the `unknown_ip_*` counters must stay 0), and the nightly GitHub Actions workflow `.github/workflows/live-smoke.yml` (Pushover alerts need the repository secrets `PUSHOVER_API_TOKEN` and `PUSHOVER_USER_KEY`).
- Local checks: `make test-api-local` starts the OpenAI stub and both Workers itself (the API built with `ZQS_FAULT_INJECTION=1` for the `transactionSync` rollback checks), runs every check through the site's binding, then stops everything. Never deploy a build made with `ZQS_FAULT_INJECTION`.

## Workflow notes
- Before handoff, run `make build` and `make test` so the maintainer can refresh the live site with confidence.
- Typical deploy loop: `make build && make test`, commit, `git push` (Workers Builds redeploys the site automatically), then `make deploy-api` whenever `api/` or `static/data/` changed (the API embeds the curated data at build time) or when `/api/version` should report a bumped `VERSION`, and only then run `make autotest AUTOTEST_FLAGS="--no-pushover"` to smoke-test production.
- `make deploy-api` refuses uncommitted tracked changes because `/api/version` reports the HEAD commit; commit the regenerated artifacts first (remember `static/build_id.js` and `static/pkg/**/*`).
- `static/build_id.js` is tracked; always include the regenerated file produced by `make build` in your commits so the auto-deploys never fall back to the `?build=dev` cache-buster.
- `make autotest` fails fast if the deployed `build_id.js` ever falls back to `"dev"`, ensuring production assets are tied to a real commit. `--api-base-url https://zqsdev-api.aleqsd.workers.dev` sends only its `/api/*` checks to the API canary.
- Extend the automated test suite for every new feature or bugfix fix to keep coverage trending upward.
- Run `python3 scripts/validate_knowledge.py` after editing `static/data/*.json`. Keep historical projects, publications and testimonials. Legacy RAG scripts are retained only for forensic inspection; never run paid upserts as part of a normal release.
- After deploying, run `make autotest AUTOTEST_FLAGS="--no-pushover"` (default base URL `https://zqsdev.com`; `www` redirects and breaks `POST /api/ai`) to ensure `/api/ai` returns factually correct answers with validated `sources` IDs.
- `KNOWLEDGE_UPDATED` comes from `updated_at` in `static/data/profile.json` at build time; bump that date when the curated data is reviewed.
- After editing `static/cv/*.html`, regenerate the PDFs with `python3 scripts/render_cv_pdfs.py` (Chrome + `pip install pymupdf`; `--check` previews the text diff without writing). It reuses the 1254px portrait embedded in the current PDF, which is not a web asset.
- Use the hidden `version` terminal command (or `make version-check`) to verify the frontend and backend are running the same release and to grab the GitHub commit links directly from production.
- If `make version-check` reports an outdated backend version or commit, run `make deploy-api` from the matching commit; the API reports the `VERSION` and commit it was built from.

## Versioning
- The project version lives in `VERSION` and in the root `Cargo.toml` (`[workspace.package]`, used by the frontend crate); the API Worker reads `VERSION` at build time.
- **Always bump the version number _before every commit_** with `python3 scripts/bump_version.py` or `make bump-version`. Do this prior to edits so both frontend and backend artifacts report the new release identifier and the `version` command stays trustworthy. Immediately stage the updated `VERSION` file (`git add VERSION`) and run `make ensure-version-bumped` to verify the bump is present in your staged changes before committing.

## Full-context AI operations
- Model default: `gpt-6-luna`, Chat Completions, reasoning `none`, max 640 output tokens. One provider call, no automatic retry.
- The seven `static/data/*.json` sources are embedded in the API Worker at build time, bounded to 64 KB (the build fails beyond). Deploy the API after editing them.
- History is client-supplied, validated, capped to 3 user/assistant pairs and treated as untrusted. `quit`/page reload clears it.
- Requests: max 1,200 characters, 64 KiB body, two concurrent provider calls, one 16-second budget per question from the start of handling (admission included; responses within 17.5 s), 20-second browser deadline. Data fetch falls back after 4 seconds.
- Spending is reserved before a call and settled from actual usage, including cached reads and writes, in integer nano-USD. A 2xx reply that fails validation is charged its actual usage; other uncertain failures keep their reservation. Rolling limits: $0.50/min, $2/hour, $2/day, $10/30 days, plus 2,000 admitted calls per UTC day. The ledger lives in the `Ledger` Durable Object: never delete or reset it. An invalid ledger disables AI (`budget_unavailable`) while `/api/data` and classic commands keep working; repair it with `zqs_admin.py rebuild`.
- Visitor IP: `CF-Connecting-IP`, set by the Cloudflare edge and passed unchanged through the binding; `X-Forwarded-For` and `X-Real-IP` are ignored. Per-IP limits apply per visitor; global spending and concurrency limits remain effective.
- The admin token only ever travels in a JSON body: never put it in a URL, a header, a command-line argument or a log.
- Public `sources` identifies sections used by the model; it is attribution, not a guarantee of factual accuracy. Check answer facts in live evals.
- Do not delete the old Pinecone index without a separate decision; it is no longer queried.
